# Examiner Dashboard — Design-Grill Coverage Review (Round 18, decisions 81–117)

**Reviewer stance:** This round's decisions are, individually, unusually well-written — most are self-contained, give a reason, and either resolve the question or explicitly flag it as an open item (decision 112's IdP, decision 99's SLA, decision 108's tool contract). That discipline is the main reason this review is short. The 11 new diagrams are, on the whole, faithful to their source decisions — nodes, lanes, and edges track the prose closely, and the "diagram scope" cards are honest about what's deliberately left out and where to find it instead. The findings below are narrower and more surgical than the 2026-09-15 review: one real state-schema contradiction, one stale adjacent diagram that now conflicts with a new decision, one diagram whose shape risks implying the exact anti-pattern its own decision rejects, and a handful of coverage/terminology nits. Scope note: this review does not re-litigate the 2026-09-15 findings (LangGraph diagram, tool contracts, threat model, etc.) — those are tracked separately and are out of scope here.

## High

### 1. `lfi-ag-feedback-review-v1`'s card invents an `ag_status` value ("redraft") that doesn't exist in the shared-state schema
**What's wrong:** The diagram's card states the full state cycle as: *"drafted → awaiting_ag → changes_requested → ag_feedback_reviewed → redraft → awaiting_ag → approved"* (`docs/architecture/lfi-ag-feedback-review-v1.candidate.json`, second card). But `agent-specifications.md` line 25 defines `ag_status`'s actual enum as exactly five values: `drafted / awaiting_ag / changes_requested / ag_feedback_reviewed / approved` — there is no `redraft` value anywhere in the shared-state table, and ADR-0017 (the guardrail ADR this checkpoint implements) doesn't mention one either.
**Why it matters:** This is precisely the "would an engineer have to guess" test the task asks about. An engineer implementing the state machine from this diagram would either (a) try to persist `ag_status = "redraft"` and find it's not a valid enum member per the canonical schema table, or (b) correctly infer "redraft" is just a transient action/edge label, not a stored status — but nothing tells them which. The node itself (`redraft`, lane `system`) is drawn as a first-class state box identical in treatment to the real enum states around it, so the visual grammar actively suggests it's a persisted state.
**Fix:** Either add `redraft` (or equivalent, e.g. `awaiting_redraft`) as a real transitional value in `ag_status`'s enum in `agent-specifications.md` line 25 and note when it's set/cleared, or change the diagram's card and node to make clear "redraft" is an action/edge label (e.g. rename the node to "Findings Redraft Triggered" with no stored-state connotation) and drop it from the "full states" list, replacing the card text with the actual four-transition cycle the schema supports.

### 2. `lfi-workflow-phase2-meeting-v1` (older, adjacent diagram) now contradicts decision 99's new checkpoint
**What's wrong:** This diagram is not one of the 11 new Round-18 diagrams, but it depicts the same LangGraph Phase 2 pipeline and predates decision 99 (last touched at commit `a8672c3`, before `5a2cd1a` "Grill the Examiner Dashboard userflow, add ADR-0029"). Its edge list goes straight from `extract → requests → sufficiency` ("Further Submissions" → "Sufficiency Check", labeled "further submissions received") with no intervening review node. Decision 99 and its own dedicated diagram (`lfi-further-submission-review-v1`) establish that `further_submission_requests[]` must pass through a mandatory Lead/Approver per-item accept/edit/reject checkpoint — and be relayed to the LFI and round-2 documents intaken — *before* the Sufficiency Check can even be reached (per `lfi-further-submission-review-v1`'s own edge order: `review → list_final → relay → intake_round2 → sufficiency_feed`).
**Why it matters:** An engineer building the actual LangGraph graph from `lfi-workflow-phase2-meeting-v1` (which reads as "the" Phase 2 workflow diagram) would wire `extract_action_items` directly into the sufficiency-check node, silently omitting the checkpoint decision 99 explicitly added to close a stated gap. The two diagrams, read together as the task instructions ask, directly disagree about whether a human checkpoint sits between "requests drafted" and "sufficiency check."
**Fix:** Update `lfi-workflow-phase2-meeting-v1.candidate.json` to insert the further-submission-review checkpoint (and, ideally, the relay/round-2-intake step) between `requests` and `sufficiency`, or add an explicit card note cross-referencing `lfi-further-submission-review-v1.html` the way other diagrams in this set do when they intentionally don't repeat detail owned elsewhere.

## Medium

### 3. `lfi-examiner-dashboard-userflow-v1`'s node shape visually risks the "parallel UI" pattern decision 89 explicitly rejects
**What's wrong:** Decision 89 and its card are explicit: "RBAC visibility model: one screen per tab, gated actions — not parallel UIs per role... Avoids two UIs drifting out of sync." But the diagram draws `workspace → examiner_view [Examiner role]` and `workspace → leadapprover_signoff [Lead/Approver role]` as two separate downstream boxes off a role-labeled fork, both feeding into `auto_close`. Visually, this is the same shape a "two parallel UIs" design would take (a role-gated fork into two distinct destination nodes), even though the sublabels ("no sign-off" / "accept / edit / reject") and the card text correctly describe gated actions on one screen.
**Why it matters:** A diagram is read structurally before its labels are read carefully — the fork-into-two-boxes shape is the exact visual pattern the decision's own language ("not parallel UIs") warns against conflating with the real model. A reader skimming node shapes (not the card prose) could walk away thinking Examiner and Lead/Approver land on different screens.
**Fix:** Collapse `examiner_view`/`leadapprover_signoff` into a single `workspace` node with an internal sublabel like "gated: sign-off controls (Lead/Approver only)" and route both roles through it before `auto_close`, or add an explicit connecting edge/annotation showing they're the same screen with different visible controls, not different destinations.

### 4. Decision 111 (Setup tab post-creation edits) has no diagram, despite its structural twin (decision 93) getting one
**What's wrong:** Decision 93 (Intake manual override: Lead/Approver-only, required reason, logged as a distinct event type) got its own diagram, `lfi-intake-tab-v1`. Decision 111 is the same pattern applied to Setup fields — Lead/Approver-only edit after creation, logged as a distinct "setup corrected" audit event — but `lfi-setup-tab-sequence-v1`'s own scope card explicitly limits itself to "examination creation (decisions 82, 85, 86)" and doesn't touch decision 111 at all. No other diagram covers it either.
**Why it matters:** Not a genuine ambiguity (the prose in `agent-specifications.md` line 130 and ADR-0029 is clear enough to implement from), but it's an inconsistent editorial choice: two decisions with an identical shape (gated correction + distinct audit-log event type), one diagrammed, one not. Worth closing for symmetry, not because an engineer would be blocked.
**Fix:** Either extend `lfi-setup-tab-sequence-v1` with a second segment for post-creation edit + "setup corrected" logging, or explicitly note in its scope card (the way other diagrams do) that decision 111 is intentionally left to prose and why.

### 5. Decision 97 (per-question supervision sign-off) has no diagram, unlike its structural siblings
**What's wrong:** Decisions 95/96 (Gap Analysis resolution), 99 (further-submission review), and 101 (Findings sign-off) — all "per-item accept/edit/reject checkpoint" patterns — each got a dedicated diagram. Decision 97, the *first* checkpoint in the HITL table and structurally identical (per-question accept/edit/reject, list-level completion once every item has a disposition), has none among the 11, and the older `lfi-workflow-phase2-meeting-v1` diagram doesn't show it either (it starts at "Phase 1 Complete: Qs finalized," after the sign-off has already happened).
**Why it matters:** Same as Finding 4 — not an ambiguity, since `agent-specifications.md` line 76 and line 134 describe it clearly, but it's a coverage inconsistency: readers get a diagram for three of four structurally identical checkpoints and have to infer the fourth follows the same pattern from prose alone.
**Fix:** Low-cost fix given how similar it would be to `lfi-gap-analysis-resolution-v1`'s layout — worth adding if another pass touches these diagrams, not urgent enough to block anything on its own.

## Low

### 6. "Lead/Approver" vs. "Lead-Approver" spelling is inconsistent, including within single files
**What's wrong:** Both `lfi-examiner-dashboard-userflow-v1.candidate.json` and `lfi-audit-log-scope-v1.candidate.json` use "Lead/Approver" in most places but "Lead-Approver" in specific spots (e.g., the lane label `"Examiner / Lead-Approver"` at userflow line 155 and audit-log-scope line 11/73), while every other diagram uses "Lead/Approver" exclusively. This isn't diagram-introduced — the design-grill log itself is inconsistent (decision 106 writes "Examiner/Lead-Approver," decisions 89/92/93/etc. write "Lead/Approver") — the diagrams just faithfully inherited it.
**Why it matters:** Cosmetic, not a comprehension blocker, but worth a global find-and-replace pass so the two spellings don't read as two different things to a new reader.
**Fix:** Pick one form (recommend "Lead/Approver," the majority usage) and normalize across `.scratch/lfi-examination-pipeline/design-grill.md`, `docs/adr/0029-*.md`, `agent-specifications.md`, and the affected `.candidate.json` files.

### 7. Portfolio home / tab-unlock-by-data-availability (decision 83) is asserted in prose and ADR text but never actually drawn, even in the diagram whose title promises navigation
**What's wrong:** `lfi-examiner-dashboard-userflow-v1`'s title is "Examiner Dashboard — Navigation & RBAC Userflow," and decision 83 (tabs unlock by data availability, not a hard phase-stepper — explicitly called out as needed because of the AG/pre-exit revision loops) is arguably the single most novel navigational rule from this round. The diagram collapses all seven tabs into one opaque `workspace` node ("7 tabs, Setup → Audit Log") and never shows the unlock condition. (`lfi-setup-tab-sequence-v1` does show one instance of it — "setup complete — Intake unlocks" — but that's incidental to a different diagram's scope, not a general treatment.)
**Why it matters:** Low severity because the rule itself (unlock = data availability, not a gate) is simple enough to state in one sentence and is stated clearly in ADR-0029 and the design-grill log — nothing here is ambiguous. It's a missed opportunity given the diagram's own title, not a gap that blocks implementation.
**Fix:** Optional: add a small card note or a sublabel on the `workspace` node clarifying "each tab unlocks independently once its data exists — see ADR-0029" so the diagram doesn't imply a stricter gating model than what was decided.

## Verdict

Examiner Dashboard requirement coverage from Round 18 is **close to implementation-ready, not fully there** — this is a materially better state than the 2026-09-15 whole-system review, and none of the findings above are "invent the design from scratch" gaps. The one finding that would actually cause rework if uncaught is **Finding 1** (the `redraft` state that doesn't exist in the canonical `ag_status` schema) — an engineer would build against the diagram, hit the schema, and have to guess or ask. **Finding 2** (the stale Phase 2 workflow diagram contradicting decision 99) is a real risk specifically because it's easy to miss — the contradiction is between two diagrams, not a diagram and prose, and nothing flags the older one as outdated. Everything else here (Findings 3–7) is a clarity/consistency polish pass, not a blocker: the underlying decisions themselves are unambiguous, and where a diagram is thin or missing, the prose in `agent-specifications.md` and ADR-0029 already carries enough detail to implement correctly. Fix Findings 1 and 2 before an engineer starts wiring the LangGraph state machine or the Phase 2 subgraph; the rest can be cleaned up opportunistically.
