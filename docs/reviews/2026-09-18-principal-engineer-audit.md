## 1. Overall verdict

**Not yet fully implementation-ready, but materially closer than two days ago, and the gap that remains is narrow and well-characterized.** The 2026-09-17 review's six blocking conditions — ADR-0003's third checkpoint, both AG/pre-exit redraft loops routed through re-signoff, the `audit_log[]` schema and `log_checkpoint()` contract, the examination-record state fields, the `severity` enum collision, and the `all_submitted`/round-2-intake mechanism — have genuinely been fixed at the build-substrate level (`agent-specifications.md`, `tool-contracts.md`) and in the canonical Phase-3 LangGraph diagram. Three new ADRs (0030–0032) close the three non-blocking items that review asked for a written position on (prompt injection, language scope, document-content storage). This is real, verifiable remediation, not narration — I checked each fix against the artifact it touches, not just the "resolves audit X.Y" comment claiming it.

What keeps this from a clean pass:

1. **The architecture-diagram-level findings from the same 2026-09-17 review (its Dimension 1, items 1.1–1.7) were not touched at all.** The deployment diagram still draws SFTP straight into Intake Tracker with no `ingestion_adapter` component; three platform services with full tool contracts (`severity_rubric`, `quant_analysis`, `template_fill`) still appear in no architecture diagram; the Notice Corpus Manager is still absent from the deployment diagram. These are cheap fixes that simply didn't make this round's punch list.
2. **The newly-created sequence diagrams (this review's specific mandate) introduce one genuine new contradiction and preserve one stale regression**: `lfi-ag-feedback-review-sequence-v1` skips the mandatory re-signoff its own sibling diagram (`lfi-workflow-phase3-postexam-v1`) draws explicitly, and `lfi-workflow-phase2-meeting-v1`'s card text still asserts the exact wrong trigger (`all_submitted`) that `agent-specifications.md` and the brand-new `lfi-further-submission-review-sequence-v1` both correctly replaced with `round_submitted(N)`.
3. **The single highest-risk generic interaction — `interrupt()` resolution under ADR-0018 §3's optimistic-concurrency/etag protocol — still has no sequence diagram**, a gap the prior review named (3.8) and that a full round of new sequence diagrams did not close, despite creating diagrams for eight other, lower-risk interactions.

None of these are on the scale of the six items that were blocking; they're the next tier down. My recommendation mirrors the prior review's shape: **proceed with Phase 1/Setup/Intake build**, but close finding #1 below (the AG-feedback re-signoff gap) before anyone builds the Approval tab or Approval Coordinator from the sequence diagram alone, and put the Dimension-1 diagram fixes on the board — they're inexpensive and have now been sitting open across two review cycles.

## 2. Industry-benchmark comparison

**C4 model (c4model.com, Simon Brown).** The repo has a genuine Context diagram (`lfi-pipeline-context-v1`) and a Container-level diagram (`lfi-pipeline-v1`) — the two levels C4's own guidance says are sufficient for most teams ("Context plus Container is enough... Component diagrams are optional"). No Component-level (L3) diagrams exist for the four LLM agents, which is *appropriate for this project's stage*: C4's own guidance is to build L3 only when it adds value, and this repo substitutes `agent-specifications.md`'s per-agent contracts (inputs/outputs/tools/guardrails) for what an L3 diagram would otherwise carry in boxes-and-arrows form — arguably a better fit for agents whose real structure is "one ReAct loop calling four tools" rather than a multi-class internal architecture. This is **appropriate-for-stage, not behind**. Where the repo is genuinely thin against C4 discipline: a Component diagram (or even a short components table) for Compliance Analyst specifically would earn its keep, since it's the one agent with real internal branching (grounding guardrail → supersession check → verdict) that today lives only in prose plus a sequence diagram scoped to one sub-slice of it.

**UML sequence diagrams (OMG UML 2.5.1; practitioner references via Sparx Systems, uml-diagrams.org).** The standard's combined fragments — `alt` (mutually exclusive branches), `opt` (single conditional branch), `loop` (repetition with guard) — are exactly the vocabulary this system's sequences need: Compliance Analyst's per-clause retry loop, the Gap Analysis "two options" branch, the per-item accept/edit/reject loops in every sign-off sequence. Archify's sequence type has no literal fragment-frame primitive; every one of the new diagrams substitutes an edge label or a card note ("loop until every item resolved", "loop: next undisposed question"). **This is a real, disclosed expressiveness gap, not sloppy authoring** — each diagram's "Diagram scope" card is honest about what isn't drawn, and a text label for a simple loop-until-done pattern is an adequate substitute. It stops being adequate for two things this repo's own tool contracts say are real, distinct branches and that no diagram anywhere renders even as a label: (a) the retry-then-give-up branch on every tool call (`tool-contracts.md`'s four-to-two-attempt backoff policies, each with a named terminal failure state), and (b) the optimistic-concurrency conflict branch on `interrupt()` resolution (ADR-0018 §3). A UML `alt` frame with an "on conflict" operand is exactly the notation this second case wants, and archify can express it as a labeled branch edge the same way the "sufficient/insufficient" branches already are — the tool isn't the blocker, the diagram just wasn't drawn.

**arc42.** The template's 12 sections map onto this repo about as well as a generic template maps onto any real project: Introduction & Goals ≈ README + CONTEXT.md; Context & Scope ≈ `lfi-pipeline-context-v1`; Building Block View ≈ `lfi-pipeline-v1` + agent-specifications.md; Runtime View ≈ the workflow/sequence diagrams; Deployment View ≈ `lfi-pipeline-deployment-v1`; Crosscutting Concepts ≈ ADR-0017/0018/0019; Architectural Decisions ≈ `docs/adr/`. Two arc42 sections are genuinely underrepresented: **Quality Requirements as a quality tree with concrete scenarios** (arc42 §10) — this repo states quality goals informally throughout (grounding accuracy, human-agreement rate) but never as a scenario table ("stimulus / response / measure"), which would sharpen ADR-0022's capacity placeholders and the human-agreement-rate metric into testable acceptance criteria; and **Risks & Technical Debt as a standing, prioritized list** (arc42 §11) — this repo's closest equivalent is the decision log's "Open items" section plus scattered "flagged as open item" sentences, which is functionally similar but not consolidated into one risk register with owners, which a project heading into implementation will want.

**Documenting HITL/approval-gated AI systems.** This is a genuinely thin literature to benchmark against, and I won't force citations beyond what's credible — most public material (Redis's "AI Human in the Loop" pattern writeup, Velt's HITL workflow guide, Tungsten's enterprise-governance piece) converges on a small set of ideas this repo already implements well: a **three-tier reversibility model** for what requires a gate (this repo's HITL table is stricter than that — every regulatory-facing artifact gates, not just irreversible ones, which is the right call for a regulator, not a gap); and **logging the proposal, the policy decision, the approver, and the outcome before execution** (matches `AuditLogEntry`'s `state_before`/`state_after`/`resolution`/`edit_diff` shape closely). One point worth naming explicitly: EU AI Act-style guidance states auditability requires capturing "reviewer identity, timestamp, rationale, model version, and confidence metrics" — this repo's `AuditLogEntry` has reviewer identity, timestamp, and (via `model_version` on the state object, not the log entry) model version, but **no confidence/score field on `compliance_verdicts[]` or `findings[]` entries** — a `supersession_graph.check()` confidence score exists as a transient tool-call return value but is never persisted onto the record it gated. For a regulator that may someday need to reconstruct "how confident was the system when a human accepted this," that's a real, cheap gap — not flagged by either prior review, adding it here.

## 3. Findings

### Finding 1 — `lfi-ag-feedback-review-sequence-v1` omits the mandatory re-signoff its own sibling diagram draws — **High**

**File**: `docs/architecture/lfi-ag-feedback-review-sequence-v1.candidate.json`

Its message sequence, in order:
```
7. examiner_app -> findings_author | confirmed summary → trigger redraft
8. findings_author -> examiner_app | redraft complete
9. examiner_app -> audit_trail    | log_checkpoint(ag_status: awaiting_ag)
10. examiner_app -> lead_approver | resubmit for AG review
```
Between message 8 ("redraft complete") and message 9 (`ag_status → awaiting_ag`), `agent-specifications.md`'s Approval Coordinator guardrail is explicit: *"a redraft is not exempt from either sign-off. It re-enters at `draft_findings`... and must pass **both** Findings/severity sign-off and Pre-AG Sign-off again before `ag_status` can reach `awaiting_ag` a second time."* `lfi-workflow-phase3-postexam-v1.candidate.json` draws this correctly — both redraft edges (`feedback-redraft`, `preexit-redraft`) route back to `draft_findings`, which flows through `findings_signoff` and `pre_ag_signoff` again before reaching `ag_showcase`. The sequence diagram's own card even paraphrases the rule correctly in prose ("ag_status has exactly 5 values... 'redraft' is Findings Author's action on confirm") but the **message list itself** jumps straight from redraft completion to `awaiting_ag`, with no messages for the two re-signoffs in between. A builder implementing the Approval tab's redraft flow from this sequence diagram alone — which is exactly what a sequence diagram is for — would wire the redraft directly back into `awaiting_ag`, recreating the exact defect (severity can change and reach the AG unreviewed) that this checkpoint exists to close, and that the 2026-09-17 review rated its single highest-consequence finding (its 2.3).

**Fix**: insert two messages between "redraft complete" and the `awaiting_ag` log entry — `findings_author -> lead_approver: findings re-signoff (severity re-validated)` and `lead_approver -> examiner_app: Pre-AG re-signoff` — mirroring `lfi-findings-signoff-sequence-v1`'s own message shape, or add an explicit `ref` note pointing at that diagram for the two re-signoff calls rather than eliding them silently.

### Finding 2 — `lfi-workflow-phase2-meeting-v1`'s card still asserts the wrong `all_submitted` trigger, contradicting the diagram created in the same round to fix it — **High**

**File**: `docs/architecture/lfi-workflow-phase2-meeting-v1.candidate.json`, card "New: sufficiency-check gate", second bullet:
> *"'Insufficient' re-enters Phase 1's Intake Tracker **via the same `all_submitted` trigger** for another document-collection round."*

This is precisely the ambiguity the 2026-09-17 review's finding 2.7 identified as unimplementable, and `agent-specifications.md` was explicitly rewritten to fix it: *"gated by Intake Tracker's `round_submitted(round: N+1)` event, **not** `all_submitted` — that event is Phase 1's Gap Analysis trigger specifically and must not re-fire on further-submission rounds (resolves audit finding 2.7)."* The brand-new `lfi-further-submission-review-sequence-v1.candidate.json`, built in this same batch of diagrams, gets this right: *"firing `round_submitted(2)` into Sufficiency Check, not Gap Analysis's `all_submitted` (fixes audit 2.7)."* So two diagrams shipped in the same round now directly disagree with each other on the one mechanism the prior review flagged as the second Critical finding in the whole document set, and the older, canonical one — the diagram `agent-specifications.md` §5 tells implementers to read first — is the one still wrong. The diagram's own `mainPath`/edges don't repeat the error (edge `requests → sufficiency` is edge-labeled, not `all_submitted`-labeled), so this is a card-text regression left behind by a partial edit, not a structural one — but it's exactly the kind of stale cross-reference a builder skimming cards for the trigger name would copy verbatim.

**Fix**: one-line edit — replace "via the same `all_submitted` trigger" with "via Intake Tracker's `round_submitted(round: N+1)` event, not `all_submitted`" to match `agent-specifications.md` and `lfi-further-submission-review-sequence-v1` exactly.

### Finding 3 — No sequence diagram exists for `interrupt()` resolution's optimistic-concurrency protocol, still — **High**

Carried forward from the 2026-09-17 review's 3.8, unresolved despite eight new sequence diagrams shipping since. ADR-0018 §3: *"Every `interrupt()` carries a version/etag. A second concurrent resolution attempt on an already-resolved checkpoint is rejected with an explicit conflict — never silently overwritten, never double-applied."* None of the 8 new per-checkpoint sequence diagrams (`lfi-intake-tab-sequence-v1`, `lfi-gap-analysis-resolution-sequence-v1`, `lfi-supervision-signoff-sequence-v1`, `lfi-ag-feedback-review-sequence-v1`, `lfi-further-submission-review-sequence-v1`, `lfi-findings-signoff-sequence-v1`, `lfi-audit-log-scope-sequence-v1`, `lfi-rubric-editor-sequence-v1`) shows the etag being issued, carried, or checked — every checkpoint-resolution message (e.g. `lead_approver -> examiner_app | accept: insufficient`) is drawn as if resolution is always uncontended. This is the one mechanism common to *every* checkpoint in the system (two Lead/Approvers on the same examination, or a double-submit from a slow UI, would exercise it), and it's currently unwritten in diagram form anywhere — only named in ADR-0018's prose.

**Fix**: either add the etag to one representative sequence diagram (e.g. `lfi-gap-analysis-resolution-sequence-v1`, since it's already the "two options" one) with a conflict branch, or build one small dedicated `interrupt()`-resolution sequence diagram the way `lfi-guardrail-citation-grounding-v1` exists as the one dedicated diagram for the grounding retry mechanism.

### Finding 4 — Deployment diagram still has no `ingestion_adapter` component; SFTP drawn straight into Intake Tracker — **High** (carried forward, unresolved from 2026-09-17 review's 1.1)

**File**: `docs/architecture/lfi-pipeline-deployment-v1.candidate.json`. Edge `workspace-to-intake`: `{"from": "lfi_workspace", "to": "intake_tracker", "label": "SFTP"}`. `lfi-pipeline-v1.candidate.json` still correctly models `lfi_workspace → ingestion_adapter → intake_tracker`, and ADR-0006 still calls the adapter boundary load-bearing for the eventual Smart Portal swap. The deployment diagram — the one artifact whose `engineering_profile: "deployment-ownership"` forces every component to carry a team `tag` — has no `ingestion_adapter` node to own. Unchanged since the prior review; not touched in this round's diagram work.

### Finding 5 — Three platform services with full `tool-contracts.md` entries appear in no architecture diagram — **High** (carried forward, unresolved from 2026-09-17 review's 1.2)

`severity_rubric`, `quant_analysis`, and `template_fill` each have a complete input/output/timeout/retry contract in `tool-contracts.md` and are referenced by name across `agent-specifications.md`, yet none appears as a component in `lfi-pipeline-v1.candidate.json` or `lfi-pipeline-deployment-v1.candidate.json` (confirmed by node listing — 15 components in the deployment diagram, none named `severity_rubric`, `quant_analysis`, or `template_fill`). `severity_rubric` gets a passing mention inside `lfi-rubric-editor-sequence-v1` as `rubric_service`, but the deployment diagram — the artifact whose whole point is "who owns and runs what" — has no home for any of the three. `template_fill` in particular returns a `document_ref` into an undiagrammed document store.

### Finding 6 — `lfi-audit-log-scope-sequence-v1` omits `log_checkpoint()`'s own documented error branches — **Medium**

**File**: `docs/architecture/lfi-audit-log-scope-sequence-v1.candidate.json`. This diagram exists specifically to draw the audit trail's single write path, and its message list is entirely happy-path: `log_checkpoint(...)` → `{status: ok, entry_id, entry_hash}`. `tool-contracts.md`'s `log_checkpoint` contract defines two named error outcomes — `duplicate_idempotency_key` (benign, treat as success) and `chain_integrity_violation` ("a correctness alarm, not a transient failure... must halt and page, never silently retry past it"). Of all the tool-error branches left undrawn across the new sequence diagrams (see Finding 7), this is the one that most deserves a branch on the diagram whose entire subject is this write path — `chain_integrity_violation` is the one failure mode in the whole system that the contract says must stop everything, and a reader of this diagram alone would not know it exists.

**Fix**: add a branch message (`audit_trail -> log_checkpoint | {status: error, reason: "chain_integrity_violation"} → halt & page`) — one line, high value given what this diagram is for.

### Finding 7 — None of the 8 new sequence diagrams show a tool-call retry/timeout/exhaustion branch, unlike `lfi-guardrail-citation-grounding-v1` — **Medium**

Every new sequence diagram (`lfi-intake-tab-sequence-v1` through `lfi-rubric-editor-sequence-v1`) is drawn happy-path-only and explicitly defers retry/error handling to `tool-contracts.md` via a "Diagram scope" card note (e.g. `lfi-intake-tab-sequence-v1`: *"Every write here routes through `log_checkpoint()`... same single write path"* — but no error branch drawn). This is a defensible, disclosed scoping choice for most of them (a UI accept/edit/reject loop genuinely doesn't need its tool-failure paths re-derived on every diagram), and it's consistent with `docs/adr/0023-testing-canary-rollback-strategy.md`'s deliberate deferral of "full TDD-style sequence diagrams for every internal REST call." But it does create a real asymmetry with the one diagram (`lfi-guardrail-citation-grounding-v1`) that predates this round and *does* draw a retry branch — a reader comparing diagrams would reasonably wonder why citation grounding gets a drawn retry loop and `ingestion_adapter.list_documents()` (which has its own distinct `adapter_unreachable`/`auth_failed` terminal-vs-transient split in `tool-contracts.md`) doesn't. Not blocking; worth a one-line "why" note in each diagram's scope card rather than silence, or picking one or two of the highest-risk ones (Intake Tracker's SFTP poll, given `ingestion_adapter.fetch_document`'s size-cap/malicious-content surface) to draw fully.

### Finding 8 — Notice Corpus Manager still mistyped/absent across diagrams — **Medium** (carried forward, unresolved from 2026-09-17 review's 1.3)

`agent-specifications.md` is unambiguous: *"Persona: none — a UI-driven ingestion workflow, not an LLM agent."* `lfi-pipeline-v1.candidate.json` still types `notice_corpus_mgr` as `messagebus` ("LLM Agent + Tool Call" per that diagram's own legend), and it is absent entirely from `lfi-pipeline-deployment-v1.candidate.json`'s 15-component list, despite being in-app v1 scope per ADR-0029. Unchanged since the prior review.

### Finding 9 — Deployment diagram draws only one representative edge for LLM inference, DB persistence, and observability, with no "representative, not exhaustive" annotation — **Medium** (carried forward, unresolved from 2026-09-17 review's 1.4)

`clarification_agent → llm_inference` is the only edge into the LLM Inference Service, though ADR-0019 requires all 4 LLM agents to hold mTLS routes there; `findings_reporting → oracle_db` is the only DB-persistence edge, though the state table is persisted "after every node execution"; `ag_preexit → observability` is the only OTel edge, though ADR-0016 requires every agent/service to emit. The diagram's own convention elsewhere annotates elision explicitly (`secrets-to-intake`: *"SFTP creds (+ DB/mTLS — not drawn)"*) — that same annotation pattern simply wasn't applied to these three edges.

### Finding 10 — No confidence/score field persisted on `compliance_verdicts[]` or `findings[]` — **Medium** (new, not raised by either prior review)

`ComplianceVerdict`'s schema (`agent-specifications.md`, "element schemas" section) is `{ question_id, verdict, citation?, asserted_by }` — no confidence score, even though `supersession_graph.check()` returns one (`confidence: float`) that gates the `needs_human_review` routing decision. Once that decision is made, the number itself is discarded rather than persisted onto the record. Per the industry-benchmark section above, audit trails for gated-AI decisions are increasingly expected to carry the model's confidence at time of human review, not just the binary outcome. This doesn't block anything today, but it's a cheap schema addition now (one field on `ComplianceVerdict`) versus a real migration later once real examinations are in flight (ADR-0025's migration-required-for-breaking-change policy would apply).

### Finding 11 — `ag_preexit` / Approval Coordinator still typed as pure "Deterministic tool" despite carrying an LLM — **Low** (carried forward, unresolved from 2026-09-17 review's 1.5)

`lfi-pipeline-v1.candidate.json` and `lfi-pipeline-deployment-v1.candidate.json` both type Approval Coordinator `cloud` ("Deterministic tool / rule-based service — no LLM involved at all" per the diagrams' own legend), with a tag "+ guarded LLM assist" bolted on to compensate. `lfi-ag-feedback-review-v1` types the same agent's summarize node `messagebus` (LLM+tool). Cosmetic, but this is the one agent whose LLM usage is the subject of an entire guardrail ADR (0017).

### Finding 12 — Context diagram still draws notice ingestion as a system-to-system feed, and still omits the Auditor role — **Low** (carried forward, unresolved from 2026-09-17 review's 1.6/1.7)

`lfi-pipeline-context-v1.candidate.json`: edge `notice-to-pipeline` = `{"from": "notice_source", "to": "pipeline", "label": "publishes notices/clauses"}`. ADR-0029 established that notices are uploaded by a human Lead/Approver in-app, not received from a publishing system — Notice Corpus Manager's whole existence is because "there is no external owner for this data." At Context zoom this should be the Lead/Approver actor (already drawn for other purposes) uploading, not a fourth external system. Separately, the actor set (`lfi`, `shared_workspace`, `notice_source`, `identity_provider`, `edm`, `examiner_team`, `assistant_governor`) still has no Auditor/Compliance Reviewer, despite ADR-0024 giving that role standing read access to the system's most sensitive store.

### Finding 13 — `lfi-gap-analysis-resolution-sequence-v1` doesn't disambiguate `asserted_by` for the "accept as insufficient" path — **Low**

**File**: `docs/architecture/lfi-gap-analysis-resolution-sequence-v1.candidate.json`, message: `examiner_app -> state_store | write compliance_verdicts[verdict: insufficient_grounding]`. `ComplianceVerdict.asserted_by` is `"model"|"human"`; the diagram's other branch explicitly labels `asserted_by: "human"` for the manually-asserted-citation path, but this branch's message doesn't state whether accepting the model's own `insufficient_grounding` flag counts as `asserted_by: "model"` (the model produced it) or `"human"` (a human made the accept decision). Almost certainly `"model"` by the schema's intent, but it's the one place in this diagram where the pattern it establishes elsewhere (label the `asserted_by` value explicitly) isn't followed through.

## 5. Dimension 3 checklist — diagrams needing more explanatory card text

This is a genuine strength of the current corpus: every diagram carries 2+ cards with 4+ substantive items, consistently explaining *why* a shape was drawn the way it was (not just restating node labels), and consistently cross-referencing the specific decision/ADR/audit-finding that shaped it. I did not find any diagram that reads as boxes-and-arrows a reader has to reverse-engineer. The list below is genuinely secondary polish, not a backlog of thin diagrams:

1. **`lfi-findings-signoff-v1`** (the Dashboard-workflow, non-sequence version) — 8 nodes but only 4 card items, the lightest ratio of any diagram in the set. Given it's the one screen modeling two parallel, never-merged analysis tracks (the single most-repeated rule in the whole decision log, ADR-0009/0011), it would benefit from a third card item spelling out *why* the two tracks are drawn as separate lanes rather than assuming the reader arrives having already read ADR-0009.
2. **`lfi-examiner-dashboard-userflow-v1`** — the single entry point for a reader unfamiliar with the project (it's what `docs/index.html`'s gallery likely leads with for the Dashboard). 5 items across 2 cards is adequate but thin for a diagram whose job is "orient a new reader to the whole app before they open any tab-specific diagram" — a short "how to navigate from here" card pointing at which of the 8 tab-specific workflow/sequence diagram pairs to open next would help more than the diagram's own content would.
3. **`lfi-pipeline-context-v1`** — good cards, but per Finding 12, the notice-ingestion edge's card text doesn't flag the ADR-0029 tension it's actually sitting on; a reader has no way to notice the diagram might be stale without independently knowing ADR-0029 exists.
