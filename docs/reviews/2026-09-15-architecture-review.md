# Architecture Review — LFI Examination Pipeline v1

**Reviewer stance:** This is a solid domain model with genuinely good instincts in a few places (the citation-grounding hard rule, treating AG/pre-exit loops as routine state, human-agreement-rate as the trust metric) — but "feels hollow" is the right diagnosis, and it's hollow in a specific, fixable way: every artifact stops at the *decision* layer and never reaches the *contract* layer. ADRs say what was decided and why; the agent-spec names tools in prose; the diagrams show boxes and arrows. Nowhere is there a tool's actual input/output schema, an error-handling policy, a state-machine diagram with every transition and failure edge, a threat model, a capacity number, or a test plan. None of that is exotic for a production LLM system in a regulated environment — it's the baseline. This is not ready to move into implementation as-is: an engineer handed these documents today would have to invent the failure semantics, the guardrail enforcement code, and the concurrency model from scratch, which means the documents aren't actually specifying the system, they're describing it. Fix the Critical and High items before writing code, not after.

---

## Critical (blocks production deployment)

### 1. No enforcement mechanism specified for any guardrail except citation-grounding
**What's missing/wrong:** ADR-0004's citation-grounding rule is explicitly called out as "enforce in code, not just the prompt" (agent-specifications.md line 49). No other agent has an equivalent code-level guardrail specified. Findings & Reporting Agent's severity assignment relies on `severity_rubric.lookup(finding)` being called, but nothing says the agent's stated severity is *validated* against that lookup's return value before the finding is persisted — an agent could call the tool, then narrate a different severity in its structured output, and nothing catches it. Similarly, AG & Pre-Exit Agent's "LLM may assist in summarizing AG feedback into actionable redraft notes" (line 97) has zero grounding requirement — this is the exact shape of risk ADR-0004 was written to prevent (an ungrounded assertion presented as if it came from an authoritative source — here, the AG), and it's given none of that rule's protection.
**Why it matters:** This is the textbook LLM-pipeline failure the team already correctly diagnosed once (ADR-0004's own rationale: "an ungrounded verdict that looks plausible is a compliance liability, not just a quality issue") and then didn't generalize. A hallucinated AG instruction that reaches Findings & Reporting Agent as a redraft trigger changes a regulatory document based on something no human said — worse than a bad citation, because it's downstream of the human-sign-off checkpoint the whole system is built around (ADR-0003).
**Concrete recommendation:** Add a hard rule to AG & Pre-Exit Agent's spec: the LLM-generated redraft summary must be presented back to the Lead/Approver as its own reviewable artifact (not silently passed to Findings & Reporting Agent) before it triggers a redraft — this needs its own `interrupt()`, distinct from the existing AG-approval-outcome tracking. Add a code-level assertion to Findings & Reporting Agent: persisted `severity` must equal the last `severity_rubric.lookup()` return value for that finding, or the write is rejected — mirror ADR-0004's "enforce in code" language explicitly for this.

### 2. No LangGraph node/edge/conditional-transition diagram exists
**What's missing/wrong:** Both `.candidate.json` files are logical/deployment architecture views (boxes = services, arrows = data flow between services). Neither is the actual graph the system will run — nodes, conditional edges, interrupt points, retry edges, subgraph boundaries (e.g., Gap Analysis Agent's "ReAct-style subgraph looped once per RFI question/clause pair," agent-specifications.md line 52). The AG/pre-exit revision loops in particular are described only in prose state-transition strings (`drafted → awaiting_ag → changes_requested → ...`) with no diagram showing what happens on every edge, including error edges.
**Why it matters:** This is the single most implementation-blocking gap. Whoever builds the LangGraph graph has to invent the actual node wiring from prose, which for a stateful, interruptible, multi-loop graph (five interrupt points, two revision loops, one 30-day-window persistence requirement) is exactly the kind of design that needs a diagram reviewed *before* code, not reverse-engineered from code after. This is standard practice for any nontrivial state machine — the absence here is the gap the team's own "feels hollow" instinct is picking up on.
**Concrete recommendation:** Before implementation starts, produce a state diagram (the `archify` skill already available in this environment supports `stateDiagram` input) covering every node, every conditional edge including failure/retry edges, every `interrupt()` and its resume condition, and the two revision loops end-to-end including the currently undocumented sufficiency-check loop (see Critical #3).

### 3. The architecture doesn't model the real "documents/answers sufficient?" loop shown in current_state.png
**What's missing/wrong:** `docs/reference-docs/current_state.png`'s Phase 2 shows an explicit, iterative loop: "Answer Collections for the questions" → "Answers Sufficient?" decision → if No, "Send out follow up email with unanswered questions" → loop back to "Potential Request for Additional Documents" → "Documents Sufficient?" decision → only once both are Yes does "Analyze findings" run. This is a real, modeled decision point in the actual process — and it does not appear anywhere in agent-specifications.md or either `.candidate.json`. The Clarification & Meeting Agent's post-meeting extraction is specified as a single one-shot step: extract `further_submission_requests[]` and route to Intake Tracker "next cycle" (line 73) — there's no step that evaluates whether a further submission, once received, actually resolves the gap, and no loop back into re-evaluation before findings analysis proceeds.
**Why it matters:** ADR-0010 already caught and fixed one instance of this exact failure mode (treating a routine loop in the source flowchart as a rare edge case) for the AG/pre-exit loops. The same category of error is still present for the mid-examination sufficiency check — the design grill (decision 39) confirms gap analysis is batch-triggered by `all_submitted`, but never revisits whether the *examination-meeting* follow-up cycle needs its own sufficiency gate before Findings & Reporting Agent's trigger condition ("further-submission loop, if any, resolved" — line 79) is considered met. As written, "resolved" is undefined — resolved by what check, judged by whom, on what criteria?
**Concrete recommendation:** Add an explicit sufficiency-check step (human-judged, per ADR-0003's augmentation principle — likely a Lead/Approver decision surfaced on the Examiner Dashboard, not an LLM auto-resolution) between further-submission receipt and Findings & Reporting Agent's trigger. Define what "further-submission loop resolved" means as a state value, not a prose assumption.

### 4. No failure/retry/idempotency semantics anywhere in the spec
**What's missing/wrong:** None of the following are addressed for any agent or tool: what happens when the LLM Inference Service is unreachable mid-call (no circuit breaker, no backoff policy, no defined behavior — does the graph node retry, fail the whole examination step, or queue?); what happens when a LangGraph checkpoint write to the Fraud Database fails (partial state persistence risk — ADR-0001's whole rationale is that interrupt/resume is "durable across the 30-day RFI window," but durability requires the checkpoint write itself to be transactional/idempotent, and nothing says it is); what happens when an LLM returns malformed structured output (no schema-validation-and-repair loop, no escalation path); and what happens if two Lead/Approvers act on the same `interrupt()` concurrently (RBAC says who *can* resolve one, ADR-0007, but not what stops two authorized people from resolving the same one simultaneously with conflicting decisions).
**Why it matters:** These are not edge cases for a system spanning a 30-day intake window plus indefinite AG/pre-exit revision cycles — transient LLM-service outages and concurrent-approver races are near-certain to occur in production over that timeframe. Silent double-processing of a checkpoint resolution, or a node re-run duplicating an `audit_log[]` entry, directly undermines ADR-0007's audit-trail guarantee, which is supposed to be the source of regulatory truth for what was approved and by whom.
**Concrete recommendation:** Define, per agent: (a) a retry policy (max attempts, backoff, what error is transient vs. terminal) for LLM Inference Service calls; (b) an idempotency key on every state-mutating agent invocation and on `log_checkpoint()` specifically, so a replayed/re-run node doesn't double-log; (c) an optimistic-concurrency check (version/etag) on `interrupt()` resolution so a second concurrent resolution attempt is rejected with a clear conflict, not silently overwritten; (d) a JSON-schema validation step on every agent's structured output with one automatic repair retry before falling back to `insufficient_grounding`/human escalation.

## High (should fix before implementation starts)

### 5. No threat model, and no security treatment for the LLM Inference Service specifically
**What's missing/wrong:** ADR-0015 covers identity federation. Nothing else in the ADRs or deployment JSON addresses a threat model. Concretely absent: encryption-at-rest for the Oracle Fraud Database (ADR-0014 is entirely about engine choice, silent on TDE/encryption, despite this store holding the audit trail and all AI-generated supervisory analysis); secrets management for SFTP credentials, the Oracle connection string, and any internal service-to-service auth tokens (no vault/secret-manager component exists in the deployment diagram at all); network segmentation beyond one "Private data subnet" boundary around Oracle DB only — the LLM Inference Service, which processes every piece of sensitive examination content at inference time (ADR-0013's whole rationale), sits in the same undifferentiated "On-prem deployment region" as everything else with no east-west traffic control, no mTLS between agent services and the inference service, nothing.
**Why it matters:** ADR-0013 justifies self-hosting specifically because "no examination data leaves the enterprise boundary at inference time" — but an inference service with no additional network isolation, no mTLS, and no distinct threat model is a weaker boundary than the ADR's framing implies. A compromised agent container (or a misconfigured internal route) has unrestricted lateral access to the component that sees every document, every meeting minute, and every finding in plaintext.
**Concrete recommendation:** Add a "Model/Inference security zone" boundary around `llm_inference` in the deployment diagram, distinct from the general backend region, with documented network-policy rules (only the five agent services may call it, nothing else, over mTLS). State encryption-at-rest requirement for Oracle explicitly in ADR-0014 or a new ADR. Add a secrets-management component (e.g., Vault, or CBUAE's existing enterprise secrets store if one exists — ask, don't assume) to the deployment diagram and connect it to Ingestion Adapter, `edm.query`, and the LLM Inference Service's auth.

### 6. Tool contracts are prose, not contracts
**What's missing/wrong:** Every tool listed in agent-specifications.md (`notice_corpus.search`, `notice_corpus.get_clause`, `edm.query`, `supersession_graph.check`, `severity_rubric.lookup`, `template_fill`, `ingestion_adapter.list_documents`, `ingestion_adapter.get_metadata`) is a one-line function signature with no input/output JSON schema, no error taxonomy (what does `edm.query` return if EDM/Oracle is down mid-call — an exception, an empty result, a stale-cache value?), no timeout, no rate limit, and no cost consideration (LLM Inference Service calls presumably have a per-token cost/GPU-time cost that should gate how aggressively Gap Analysis Agent's per-clause ReAct loop retries).
**Why it matters:** "Tools" in an agentic system are the actual attack surface and the actual reliability surface — an LLM calling a tool with undefined failure behavior will improvise (retry infinitely, hallucinate a plausible-looking error result, or silently treat a timeout as "no data found," which for `notice_corpus.get_clause` under the citation-grounding rule is catastrophic: a timeout must never be interpreted as "no matching clause exists," or a real clause gets silently treated as `insufficient_grounding` when it's actually a corpus-availability problem, and no verdict is produced instead of a correct one being delayed and retried).
**Concrete recommendation:** Write a one-page contract per tool: input schema, output schema (including a distinct error/timeout shape separate from "no result found"), timeout value, retry policy, and — for `edm.query` and `notice_corpus.*` specifically — an explicit statement that "system unavailable" must never collapse into the same code path as "no matching data," since the downstream behavior (insufficient_grounding vs. retry-later) differs.

### 7. `severity_rubric.lookup` is scoped as Findings & Reporting Agent's private tool but is a shared, UI-editable resource
**What's missing/wrong:** agent-specifications.md lists `severity_rubric.lookup(finding)` under Findings & Reporting Agent's tool list (line 85), but CONTEXT.md and decision 16 describe the rubric as data, editable through its own UI, independent of any one agent. As specified, it reads like an agent-owned dependency rather than a shared platform service with its own versioning.
**Why it matters:** If the rubric can be edited mid-examination-cycle (the whole point of making it UI-editable rather than hardcoded), and a finding drafted under rubric version N gets revised weeks later during an AG/pre-exit loop after the rubric has since been edited to version N+1, which version applies? Nothing addresses this. Silent rubric-version drift between a finding's initial severity and a redraft's severity is a real regulatory-consistency risk (two findings of the same type in one examination getting different deadlines because the rubric changed between drafting them).
**Concrete recommendation:** Model the rubric as a versioned shared service (not an agent-local tool); every finding record should carry the rubric version it was evaluated against; redrafts should either re-evaluate against the current version explicitly and log that as a rubric-version change, or explicitly pin to the original version — pick one and state it.

### 8. Findings & Reporting Agent's quantitative-analysis track has no defined computation boundary between code and LLM
**What's missing/wrong:** The quantitative track is described as "EDM figures analyzed on their own terms (loss ratios, volume trends)" (line 81-83) with no tool listed for doing the actual arithmetic — only `edm.query` (read-only fetch) and `severity_rubric.lookup`/`template_fill`. It's unclear whether "a loss ratio increased 40% quarter-over-quarter" (ADR-0011's own example) is computed deterministically in code and then narrated by the LLM, or computed by the LLM directly from raw EDM figures in-context.
**Why it matters:** LLMs computing ratios/trends directly from numbers in a prompt are a known, well-documented source of silent arithmetic errors, and this is exactly the kind of quantitative claim (a specific percentage, presented as fact, in a regulatory finding) that ADR-0004's grounding philosophy was designed to prevent for the qualitative track — the quantitative track has no equivalent protection at all.
**Concrete recommendation:** Add a `quant_analysis.compute(lfi_id, period_range, metric)` deterministic tool (code, not LLM) that returns pre-computed ratios/trends/deltas, and constrain the LLM's role to narrating and prioritizing those pre-computed numbers into findings — never computing them itself. Add a guardrail parallel to ADR-0004: no quantitative finding without a number traceable to a `quant_analysis.compute()` call.

### 9. No capacity/scale plan of any kind
**What's missing/wrong:** No concurrent-examination target, no GPU sizing methodology (even a rough placeholder — e.g., "N concurrent Gap Analysis ReAct loops × average tokens/verdict × target p95 latency ⇒ GPU count"), no Oracle IOPS/storage sizing, no answer for what changes operationally between 10 and 100 concurrent examinations. The observability spec mentions GPU "queue depth" as a metric (line 137) but no target threshold or alert condition is attached to it.
**Why it matters:** Without even an order-of-magnitude estimate, the on-prem GPU procurement (ADR-0013) and Oracle capacity planning (ADR-0014) can't actually be executed — "self-hosted, GPU" and "Oracle" are engine choices, not a capacity plan, and CBUAE will need to buy or provision specific hardware before go-live.
**Concrete recommendation:** Even a rough model is better than none: estimate FPSD's actual annual examination count and average concurrency (this is knowable — ask the examiner team), multiply by expected token volume per Gap Analysis run (dominant cost driver, since it's a per-clause loop), and derive a placeholder GPU count and Oracle storage/IOPS estimate explicitly marked "revisit once real usage data exists," the same way decision 30's supersession threshold is already treated.

### 10. No testing strategy beyond the golden-eval-set citation check
**What's missing/wrong:** ADR-0016 specifies an offline golden eval set gating citation-validity and a human-graded sample before any prompt/model change ships. Nothing else exists: no unit tests for tool error paths, no integration tests for the LangGraph graph's structural correctness (does resuming from a persisted checkpoint after a crash restore state correctly? does the AG revision loop actually route back to Findings & Reporting and not silently drop state?), no load test, no chaos/failure-injection test (what does the system do if `notice_corpus.get_clause` starts timing out for 30% of calls?), no staging environment story, no canary/rollback plan for a model swap (decision 49 explicitly keeps the model swappable, but there's no described process for validating a swap candidate against production traffic before fully cutting over, nor a rollback path for in-flight examinations if the new model regresses mid-cycle).
**Why it matters:** The golden-eval-set gate catches only citation quality. It does not catch a broken interrupt/resume path, a race condition, or a regressed quantitative-analysis prompt. For a system that will have examinations in-flight for 30+ days with two multi-week revision loops layered on top, a model or prompt change deployed mid-cycle with no canary and no rollback path is a real production incident waiting to happen — decision 49's "model stays swappable" framing implies this will actually happen, not a hypothetical.
**Concrete recommendation:** Add, before implementation: (a) unit tests for every tool's error/timeout path; (b) a LangGraph integration test suite exercising every interrupt/resume path and both revision loops against a simulated crash-and-resume; (c) a canary process for model/prompt swaps — run the candidate against a shadow traffic sample and the golden eval set, compare human-agreement rate on a pilot subset of live examinations before full cutover; (d) an explicit statement of what happens to examinations already mid-flight when a model swap ships (pin them to the old model version until completion, or accept behavior drift — pick one).

## Medium (should fix before v1 ships)

### 11. No data retention or lifecycle policy
**What's missing/wrong:** No retention period is defined for examination data, meeting minutes, or — most notably — Langfuse traces, which per ADR-0016 capture "the prompt, the completion, token usage" for every agent call, meaning potentially sensitive supervisory content and LFI-identifying detail lives in a second store (Langfuse) indefinitely by default. No right-to-erasure or data-lifecycle process is defined for a voided examination.
**Why it matters:** On-prem deployment (ADR-0015) answers "where," not "for how long" or "who can access it later." A regulator's own AI tooling retaining full prompt/completion transcripts of supervisory findings with no defined retention or access-review policy is itself a governance gap in a compliance department's own system.
**Concrete recommendation:** Define a retention period for Langfuse traces (shorter-lived than the Fraud Database's audit trail, which likely needs to persist per CBUAE's regulatory record-keeping requirements) and a periodic access review for who can query historical Fraud Database/Langfuse content — RBAC currently only names Examiner/Lead-Approver, with no defined "auditor" or "compliance reviewer" role for the audit-consumption use case ADR-0016 itself describes.

### 12. No shared-state schema versioning strategy
**What's missing/wrong:** The LangGraph state object (documented in agent-specifications.md's shared-state table) will evolve across releases. Nothing addresses what happens to an examination checkpointed under schema version N when the pipeline is redeployed with schema version N+1 mid-examination (a realistic scenario given 30-day intake windows plus indefinite AG/pre-exit loops).
**Why it matters:** A field rename, type change, or new required field deployed while examinations are mid-flight will break resume for those examinations unless there's an explicit migration path — this is a known LangGraph/durable-workflow pitfall, not a hypothetical.
**Concrete recommendation:** Version the state schema explicitly (a `schema_version` field on the state object itself, distinct from the diagram's `schema_version`), and require a migration function for any breaking change, tested against a representative in-flight checkpoint before a deploy ships.

### 13. RFI Store's persistence model is unspecified and diagrammed inconsistently with Notice Corpus/Audit Trail
**What's missing/wrong:** In `lfi-pipeline-v1.candidate.json`, `rfi_store` is typed `"database"` with sublabel "Excel: ID + clause" (lines 39-50) — the same component `type` as Notice Corpus and Audit Trail Store, both of which are explicitly Oracle-backed Fraud Database sub-stores (ADR-0012/0014). But decision 15 describes the RFI as literally "a structured Excel sheet," not a queryable database at all. The diagram's uniform `"database"` typing implies RFI Store has the same operational characteristics (Oracle-backed, queryable, part of the Fraud DB) as the other two `"database"`-typed components, when it may just be a file.
**Why it matters:** A new engineer reading the diagram cold will reasonably assume RFI Store is provisioned the same way as Notice Corpus/Audit Trail (i.e., inside the Fraud Database), when it might actually need its own ingestion step (Excel parsing) with different consistency/versioning properties (what happens when the RFI master template is edited — does RFI Store version that, or always reflect the latest?).
**Concrete recommendation:** Either explicitly fold RFI Store into the Fraud Database's logical sub-stores (mirroring ADR-0012's treatment of Notice Corpus/Audit Trail) and say so, or give it a distinct diagram treatment (e.g., a `sublabel` noting "flat file, not Oracle-backed") so its actual persistence model isn't implied by shared node type alone.

### 14. Deployment diagram's card color-coding is inconsistent with the logical diagram's
**What's missing/wrong:** In `lfi-pipeline-v1.candidate.json`, the card dot colors are `cyan` = "v1 scope," `violet` = "Human-in-the-loop," `emerald` = "Deferred to v2." In `lfi-pipeline-deployment-v1.candidate.json`, the same colors are reused for entirely different categories: `cyan` = "5 agents, 1 deployable service," `violet` = "HITL checkpoints" (consistent, coincidentally), `amber` = "Observability & evaluation," `emerald` = "Deployment (ADR-0013/0014/0015)" — note `emerald` means "deferred/out-of-scope" in one diagram and "in-scope deployment decisions" in the other. A reader who's just internalized the logical diagram's color key and moves to the deployment diagram will misread `emerald` as "these deployment decisions are deferred," which is the opposite of the intended meaning.
**Why it matters:** Color is a cheap, high-bandwidth signal specifically because a reader stops consciously parsing it after the first pass — an inconsistent reuse of the same color for opposite meanings across two diagrams meant to be read together is a real comprehension trap, not a cosmetic nit.
**Concrete recommendation:** Establish one fixed color→category mapping used identically across both diagrams (e.g., always reserve `emerald` for "deferred/out of scope," pick an unused color for deployment-decision cards), or drop card color entirely in favor of the section headers already present.

### 15. "5 agents" framing on the deployment diagram's own card is imprecise in a way that will bite eval planning
**What's missing/wrong:** The deployment diagram's card literally states "5 agents, 1 deployable service" and then in the same breath notes "Intake Tracker is rule-based, not LLM" (lines 418-422) — an internal contradiction (it's not an agent by the document's own persona-and-tools definition of "agent," yet the headline count includes it).
**Why it matters:** This is a small thing with a real downstream cost: whoever sets up the eval/observability plan from this diagram alone (without cross-referencing agent-specifications.md line 30's explicit "not an LLM agent" caveat) may reasonably try to wire Intake Tracker into the same Langfuse tracing/human-agreement-rate framework as the four real LLM agents, wasting effort building eval infrastructure for a deterministic rule engine that doesn't need it.
**Concrete recommendation:** Change the card to "4 LLM agents + 1 rule-based service, 1 deployable runtime" — precise, and self-consistent with its own caveat one line below.

## Low / Nice-to-have

### 16. No cost model
**What's missing/wrong:** GPU hosting cost, Oracle licensing at scale, Langfuse storage growth — none costed, even roughly.
**Why it matters:** Not blocking for architecture sign-off, but CBUAE leadership will ask before funding on-prem GPU procurement, and having zero placeholder number invites the project stalling at the budget-approval step after architecture is otherwise approved.
**Concrete recommendation:** A rough order-of-magnitude estimate (even "$X-Y per year for N GPUs at current on-prem hardware pricing") alongside the capacity plan in Finding #9.

### 17. No independent model-risk/compliance sign-off process for the AI system itself
**What's missing/wrong:** A department whose job is compliance examination is building an AI system that produces compliance judgments, with no mention of that system itself going through an internal model-risk-management or independent-validation review (standard practice in banking-adjacent regulatory contexts, e.g., the SR 11-7-style model governance a central bank would typically expect of the institutions *it* regulates).
**Why it matters:** This is a genuine irony worth naming directly: FPSD would likely expect a bank it examines to have model governance over any AI system materially influencing a regulatory outcome. Nothing here suggests FPSD is holding its own tool to that standard.
**Concrete recommendation:** Not an architecture fix, but flag to the team as an organizational/process gap worth raising with CBUAE's own model-risk function before go-live, independent of the engineering work.

## Direct answers to the team's specific questions

**Do we need 5 agents?**
Roughly right, with one internal seam worth watching. Calling it "5 agents" is itself imprecise (Finding #15) — it's 4 LLM agents (Gap Analysis, Clarification & Meeting, Findings & Reporting, AG & Pre-Exit) plus 1 rule-based service (Intake Tracker). That's a defensible, lean decomposition for v1 — it maps cleanly to the three real phases and doesn't over-fragment into per-task micro-agents. The one seam worth reconsidering is Clarification & Meeting Agent's two responsibilities (pre-meeting drafting vs. post-meeting extraction, decision 25) — different trigger, different inputs, different tools (one calls notice corpus/EDM-derived state, the other is pure text extraction with no tool calls at all), different failure modes. The spec already treats them as two sub-flows within one node, which is fine — don't split into a 6th top-level agent — but the LangGraph implementation should make them two distinct subgraph entry points, not one monolithic node with an internal if/else on trigger type, so they can be evaluated, retried, and eval-metriced independently (they already have separate golden-eval treatment implicitly, since citation-validity doesn't apply to post-meeting extraction at all). A principal engineer at Google would ship this same count for v1 but would insist on the sufficiency-check loop (Finding #3) being a real node, which would make it 4 LLM agents + 1 rule service + 1 human-gated decision node, not 5 flat boxes.

**What tools does each agent actually need, and what's missing?**
- **Intake Tracker** (rule-based): `ingestion_adapter.list_documents`, `ingestion_adapter.get_metadata` — complete for v1 scope, no LLM tools needed.
- **Gap Analysis Agent**: `notice_corpus.search`, `notice_corpus.get_clause`, `edm.query`, `supersession_graph.check` — missing: a distinct "corpus/EDM unavailable" error path from these tools that never collapses into `insufficient_grounding` (Finding #6); missing a defined sequencing contract that supersession check happens *before* a citation is finalized, not just available as a callable tool (currently implied, not enforced).
- **Clarification & Meeting Agent**: pre-meeting side needs read access to `compliance_verdicts[]`/`supervision_questions[]`/EDM context (already state, not tool calls — fine); post-meeting side correctly has no external tool calls (pure extraction) — missing: the sufficiency-check step from Finding #3, which needs its own human-decision surface, not a tool per se.
- **Findings & Reporting Agent**: `severity_rubric.lookup`, `template_fill` — missing: a `quant_analysis.compute()` deterministic arithmetic tool (Finding #8); `severity_rubric.lookup` should be promoted to a shared/versioned service rather than owned by this agent alone (Finding #7).
- **AG & Pre-Exit Agent**: correctly has no tools for the deterministic state machine — missing: a defined, grounded summarization tool/contract for the "LLM may assist in summarizing AG feedback" path (Finding #1), since right now it's an unguarded free-text LLM call with no tool boundary at all.
- **Cross-cutting missing tool**: none of the tools above have documented schemas, timeouts, or retry policies (Finding #6) — this is the most universal gap, present for every single tool listed.

**What SDLC artifacts are actually missing, and which matter most right now?**
Prioritized:
1. **LangGraph node/edge/state-transition diagram** (Critical #2) — matters most, blocks implementation directly; this is the one artifact that turns prose state-machine descriptions into something buildable and testable.
2. **Tool contracts** (High #6) — one page per tool with schema/error/timeout/retry; needed before any tool-calling code is written, not after.
3. **Data model / ER diagram for the Fraud Database's Oracle schema** — notice corpus tables, `audit_log` structure (including the hash-chain fields from ADR-0016), findings/severity tables — needed before DB implementation starts, currently doesn't exist in any file reviewed.
4. **A lightweight PRD** — not a full enterprise PRD, but a one-page statement of success metrics (what human-agreement-rate range is considered healthy vs. concerning, what latency SLAs the Examiner Dashboard needs to hit) and explicit non-functional requirements — currently these live only implicitly inside ADR-0016's metric definitions, with no target thresholds attached to any of them.
5. **Can genuinely wait**: full TDD-style sequence diagrams for every internal REST call, and the on-call/runbook doc — these matter before go-live, not before implementation starts, since the team ownership (Platform/Frontend/ML Platform/DBA/SRE tags already present in the deployment diagram) is at least sketched, and the operational doc can be written once the system exists to operate.
